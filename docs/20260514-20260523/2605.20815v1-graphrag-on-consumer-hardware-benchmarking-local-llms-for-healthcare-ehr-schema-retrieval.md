## 摘要
基于图的检索增强生成（GraphRAG）将检索增强生成扩展到支持对复杂语料库的结构化推理，但其在资源受限、隐私敏感的部署中的可靠性仍不明确。在医疗保健领域，电子健康记录（EHR）数据复杂且受到严格监管，依赖基于云的大语言模型（LLMs）会在成本、延迟和合规性方面带来挑战。在这项工作中，我们使用本地部署的开源LLMs对GraphRAG用于EHR模式检索进行了系统评估。我们在真实世界的EHR模式文档上实现了Microsoft GraphRAG流水线，并对四个模型进行了基准测试，包括Llama 3.1 (8B)、Mistral (7B)、Qwen 2.5 (7B)和Phi-4-mini (3.8B)，每个模型均通过Ollama部署在单个消费级GPU（8 GB VRAM）上。我们评估了全局和局部检索模式下的索引效率、知识图谱构建、查询延迟、答案质量和幻觉情况。我们的结果揭示了显著差异：Llama 3.1 生成的知识图谱最丰富（1,172个实体），Qwen 2.5 取得了最佳答案质量（3.3/5），Phi-4-mini 由于结构化输出错误未能完成流水线，而Mistral 表现出退化的重复行为。我们进一步表明，GraphRAG 存在一个实用的能力阈值，即低于约70亿参数的模型无法可靠地生成有效的结构化输出，从而无法完成流水线。此外，索引和答案质量在不同模型间是解耦的，局部检索在延迟和事实依据方面始终优于全局总结，且幻觉较少。这些发现表明，GraphRAG在消费者硬件上是可行的，同时凸显了模型选择和检索设计对于在受监管环境中实现稳健部署的重要性。

## Abstract
Graph-based Retrieval Augmented Generation (GraphRAG) extends retrieval-augmented generation to support structured reasoning over complex corpora, but its reliability under resource-constrained, privacy-sensitive deployments remains unclear. In healthcare, where Electronic Health Record (EHR) data is complex and strictly regulated, reliance on cloud-based large language models (LLMs) introduces challenges in cost, latency, and compliance. In this work, we present a systematic evaluation of GraphRAG for EHR schema retrieval using locally deployed open-source LLMs. We implement the Microsoft GraphRAG pipeline on real-world EHR schema documentation and benchmark four models, including Llama 3.1 (8B), Mistral (7B), Qwen 2.5 (7B), and Phi-4-mini (3.8B), each deployed via Ollama on a single consumer GPU (8 GB VRAM). We evaluate indexing efficiency, knowledge graph construction, query latency, answer quality, and hallucination under both global and local retrieval modes. Our results reveal substantial differences: Llama 3.1 produces the richest knowledge graph (1,172 entities), Qwen 2.5 achieves the best answer quality (3.3/5), Phi-4-mini fails to complete the pipeline due to structured-output errors, and Mistral exhibits degenerate repetition behavior. We further show that GraphRAG exhibits a practical capacity threshold, where models below approximately 7B parameters fail to reliably produce valid structured outputs and cannot complete the pipeline. In addition, indexing and answer quality are decoupled across models, and local retrieval consistently outperforms global summarization in both latency and factual grounding, with reduced hallucination. These findings demonstrate that GraphRAG is feasible on consumer hardware while highlighting the importance of model selection and retrieval design for robust deployment in regulated settings.

- **研究背景**：电子健康记录 (EHR) 系统依赖高度结构化的数据库模式，对其进行准确检索与分析需要理解表间、字段间的复杂关系。传统检索增强生成 (RAG) 难以有效处理跨实体、多跳推理等问题，GraphRAG 通过构建知识图谱并引入社区级摘要来支持全局推理。
- **核心问题**：GraphRAG 能否在消费者级硬件上（资源受限、隐私敏感）可靠地完成 EHR 模式检索任务？具体而言，本地部署的开源大语言模型 (LLM) 是否能够支撑起完整的 GraphRAG 流水线（包括知识图谱构建、社区总结、查询生成），并保持足够的答案质量？这与完全依赖云端 LLM 时面临的成本、延迟和合规性（如 HIPAA）挑战直接相关。
- **整体含义**：本研究旨在为医疗等强合规领域在本地化、低成本、保护隐私的条件下使用 GraphRAG 提供经验性依据，并揭示模型能力、检索模式与流水线可靠性之间的实际边界。

## 2. 论文提出的方法论

- **流水线框架**：采用 Microsoft GraphRAG v2.3.0 标准六阶段流水线。
  - 文档分块：将 HTML 格式的 EHR 模式文档切分为 512 token 的片段（重叠 256 token），共 8 个文档、141 个文本单元。
  - 实体与关系抽取：由所选 LLM 从每个片段中提取表格、列名、数据类型、外键等结构化信息，并输出为 JSON。
  - 知识图谱构建：将抽取的实体和关系组装成图，三节点形式存储表格‑列、表格‑表格关联。
  - 社区发现：使用 Leiden 算法对图谱进行多层社群划分。
  - 分层摘要：由 LLM 在每个社群层级上生成自然语言摘要，以捕获跨表的全局结构。
  - 向量嵌入：使用 `nomic-embed-text`(274 MB) 将文本单元和实体描述嵌入，支持后续基于向量的检索。
- **查询形式**：后续的在线查询分为两种模式：
  - **全局检索 (global search)**：以 Map‑Reduce 方式聚合各社区摘要，生成整体性回答。
  - **局部检索 (local search)**：基于实体邻域的向量相似度检索，返回实体相关上下文，再由 LLM 生成回答。
- **部署方式**：所有模型通过 Ollama v0.17.0 部署在本地，量化级别为 Q4_K_M，并发请求数设为 1（单 GPU 内存约束）。

- **评测指标与查询**：

## 6. 论文的主要结论与发现

- **模型能力阈值**：参数规模低于约 7B（量化）的模型无法可靠输出结构化 JSON，导致流水线中断。Phi‑4‑mini（3.8B）仅抽取 16 个实体即崩溃，提示本地部署需要至少 7B 级别的模型。
- **索引质量与答案质量解耦**：Llama 3.1 抽取的实体最多（1,172），构建的知识图谱最丰富，但答案质量仅 2.7/5（局部）；相反，Qwen 2.5 抽取实体最少（330），却取得最高的答案评分（3.3/5）。表明实体抽取能力 ≠ 最终回答能力。
- **检索模式差异显著**：
  - 局部检索在所有模型中均表现出更低的延迟（平均 30~34 秒 vs. 110 秒以上）和更高的答案质量。
  - 全局检索在高层次总结时易产生幻觉（如生成语料中不存在的 `PATIENT`、`INSURANCE` 等表名），而局部检索仅引用实际实体，事实依据更可靠。
- **失败模式识别**：
  - Phi‑4‑mini：结构化 JSON 生成失败，流水线中断。
  - Mistral：在特定查询下出现退化的无限重复输出，与缺乏重复惩罚机制有关。
- **部署价值**：本地 GraphRAG 消除了 API 调用和数据外传费用，特别有利于受 HIPAA 限制的医疗场景。局部检索模式是资源受限环境下更稳健、更低幻觉的选择。

## 7. 优点

- **系统级评估**：不局限于单一基准，而是完整考察 GraphRAG 流水线的各阶段（索引、图构建、查询），贴近真实部署需求。
- **贴近实际的受限环境**：使用单一消费级 GPU、真实医疗模式文档，对监管严格的行业有直接参考意义。
- **揭示非平凡行为**：明确指出了模型大小门槛、索引与回答能力的解耦、全局检索的幻觉风险，这些发现对后续系统设计有指导意义。
- **实用指导明确**：建议在本地部署中优先选择约 7B 以上的模型，并倾向于使用局部检索，同时给出了模型级推荐（如 Qwen 2.5 回答最佳，Llama 3.1 适合覆盖性提取）。

## 8. 不足与局限

- **数据集规模有限**：仅使用了 10 个表格的子集，难以完全反映大规模 EHR 模式（数千张表）带来的长尾、复杂依赖等挑战。
- **评估主观性**：答案质量采用人工评分，虽然准则一致，但缺少多位评估者或与标准答案的严格自动对齐，可能引入偏差。
- **单一硬件环境**：所有实验均在 GTX 1070 Ti（8 GB）上完成，未考虑不同 GPU 显存、架构或内存条件的影响，结论的泛化性需要更多硬件验证。
- **未与云端基线或其它 RAG 变体对比**：研究主要聚焦 GraphRAG 自身行为和模型间比较，缺少与标准 RAG 或云端 LLM 方案的直接质量、成本对比，无法量化本地方案相对于常规方案的绝对优劣。
- **超参数与配置固化**：并发请求固定为 1，量化统一为 Q4_K_M，未探索其他量化级别、重复惩罚参数等对失败的缓解效果。
